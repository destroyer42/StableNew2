## 1. Scope, what is accepted, and the canonical path

This document covers image-to-video: the native Stable Video Diffusion XT path and its post-processing (CodeFormer, Real-ESRGAN-style upscale, RIFE), the Comfy Video Workflow (workflow catalog, NJR builder, Comfy backend, managed Comfy runtime), the neutral video execution contract, motion sources, provenance and replay, and Movie Clips assembly. ## 2. The neutral video execution contract

Types are in `src/video/video_backend_types.py`:

- `VideoBackendCapabilities`: `tasks` (only `image_to_video` exists, `KNOWN_VIDEO_TASKS`), `controls`, `required_controls`. Controls are semantic input forms (`KNOWN_VIDEO_CONTROLS`: source image, prompt text, negative prompt, start/end/mid anchors, control video, pose video, camera intent), never model names. `stage_types` and the `supports_*` flags are legacy sugar folded into `controls` on construction.
- `VideoExecutionRequest` (neutral request, carries `task`, `requested_controls`, `workflow_id/version`, `experimental_opt_in`, `cancel_token`) and `VideoExecutionResult` (canonicalized through `src/pipeline/artifact_contract.py`; `to_variant_payload` feeds the runner).
- `VideoBackendInterface`: `backend_id`, `capabilities`, `execute(pipeline, request)`.

`VideoBackendRegistry` (`build_default_video_backend_registry`) registers two backends: `svd_native` (`SVDNativeVideoBackend`) and `comfy` (`ComfyWorkflowVideoBackend`). No backend claims the `animatediff` stage type (retired, section 9).

`VideoExecutionResolver` (`src/video/video_execution_resolver.py`) is the only place a stage becomes a validated (backend, task, controls) triple. Validation runs before any backend is called and raises `VideoContractError` with a code (`unknown_backend`, `unsupported_task`, `unsupported_control`, `missing_control`, `backend_required`, `invalid_workflow`). There is no fallback and no silent dropping of a control. Two intent sources:

- **Neutral (new work):** a `video_execution` block in the stage config (`backend_id`, `task`, `controls`, `workflow_id`, `workflow_version`, `experimental_opt_in`). The backend is chosen only by `backend_id`. `build_video_execution_block` writes it (`src/video/video_workflow_intent.py`).
- **Legacy bridge:** a stage without the block resolves through `LEGACY_STAGE_BINDINGS` and `VideoBackendRegistry.get_for_stage`.

**Trap [V]: the native SVD path uses the legacy bridge.** `_build_svd_njr` writes no `video_execution` block, so the one accepted production backend routes by stage name. The resolver's documented removal condition ("every producer compiles the neutral block") is therefore not met. Do not delete `LEGACY_STAGE_BINDINGS` or `get_for_stage` without first making SVD compile the neutral block and proving replay of existing SVD records.

Backends that need extra checks implement `validate_workflow(request)` (the Comfy backend does); `VideoExecutionResolver.apply` runs it for neutral work and stamps `context_metadata["video_contract"]`.

## 3. Native SVD XT

### 3.1 Flow

`SVDController` (`submit_svd_job`, `submit_svd_folder_batch`) validates the config (`validate_svd_postprocess_config`), runs `get_svd_preflight` (`src/video/svd_capabilities.py`; reads no model, downloads nothing), builds one NJR per source and crosses `JobService.submit_njrs`. Folder batch is non-recursive and all-or-nothing (`discover_svd_folder_sources` in `src/video/svd_preprocess.py`): any unreadable supported file blocks the batch; with "match source aspect" each source gets its own target from `select_svd_target_size` (`src/video/svd_target.py`, seven vetted stride-64 sizes near 0.6 MP).

At run time: `SVDNativeVideoBackend.execute` -> `RuntimeTransitionCoordinator.prepare_for(RUNTIME_SVD_NATIVE)` (releases StableNew-owned A1111/Comfy residency, never an external runtime) -> `Pipeline.run_svd_native_stage` in `src/pipeline/executor.py` -> `SVDRunner.run` (`src/video/svd_runner.py`):

`validate postprocess config -> SVDService.prepare_runtime (model load) -> prepare_svd_input (resize policy) -> SVDService.generate_frames -> SVDPostprocessRunner.process_frames -> export (mp4 | gif | frames, optional preview PNG) -> embed portable provenance (mp4) -> write_svd_run_manifest`.

Cancellation is checked between every phase and per denoising step (`_build_step_callback`); on any exception `SVDRunner._remove_partial_outputs` deletes only files this run created. Runtime memory is released in `finally`.

### 3.2 Config, defaults and post-processing

- `SVDConfig` (`src/video/svd_config.py`) groups `preprocess`, `inference`, `output`, `postprocess`. Supported model ids are in `src/video/svd_models.py` (`img2vid`, `img2vid-xt`, `img2vid-xt-1-1`); the default is `stabilityai/stable-video-diffusion-img2vid-xt`.
- Defaults differ by origin [V]. The dataclass default is `local_files_only=False`, 25 frames, 7 fps, motion bucket 127. `SVDController.build_default_config` and the SVD tab's "Recommended 12GB / XT 25f" preset set `local_files_only=True`, 25 frames, motion bucket 110, noise augmentation 0.02, decode chunk 8. Saved tab state that still holds the untouched pre-2026-10-20 default ("XT 14f": 14 frames, bucket 48, chunk 2) is upgraded on restore. Audit E5 ("SVD defaults to online") is true only for configs built without that key (for example a hand-built config). With `local_files_only=False`, `SVDService._load_pipeline` will download the model at job time and will fall back to a remote refresh if a cached load fails.
- Conditioning and decoding [V]: `fps` is passed to the Diffusers pipeline (SVD is micro-conditioned on it), not only used for export. `decode_chunk_size` is an upper bound: `balanced_decode_chunk_size` splits the clip into even chunks (25 frames at 8 decode as 7/7/7/4), because the temporal VAE only sees one chunk and small or uneven chunks flicker at their boundaries. An out-of-memory error is never retried or downgraded automatically; its message reports the configured and effective decode chunk, and advises lowering Decode chunk only when denoising had finished (a failure before any denoising step, such as CUDA context creation, points at GPU memory held outside the job).
- Admission (`SVDController.prepare_for_admission`, fresh submissions only; replays keep their frozen NJR) [V]: a blank or negative seed becomes a concrete random seed recorded in the job (per source in a folder batch); more frames than the model was trained for (`SVDModelSpec.max_num_frames`: 25 for XT, 14 for the base model) are refused; XT 1.1 gets its trained conditioning (`locked_motion_bucket_id` 127, `locked_fps` 6). Source images are loaded with their EXIF orientation applied and transparency composited over `pad_color`; folder-batch aspect matching uses the oriented size.
- Post-processing order inside `SVDPostprocessRunner.process_frames` (`src/video/svd_postprocess.py`) [V]: face restore, **upscale, then interpolation** (secondary motion is retired, see below). Upscale runs before RIFE so the GAN processes the N generated frames, not N x multiplier, and RIFE interpolates frames that are already at the final size. The order is code, not config: a replayed job runs in the current order. Every executed stage is recorded, in execution order, in the run manifest under `postprocess.stages` (`stage`, `frames_in`, `frames_out`, plus the model for upscale and the temporal setting for face restore). Face restore and upscale run in a helper process, `python -m src.video.svd_postprocess_worker`, which calls the StableNew-owned adapters in `src/video/restoration/` (`CodeFormerRestorer` through Spandrel plus the isolated `legacy_face_helper.py`; `RRDBUpscaler`) and leaves a small `worker_report.json` beside its frames that the runner folds into the manifest (`postprocess.face_restore.worker_report`, `postprocess.upscale.worker_report`; absent or unreadable is not a failure). Readiness is import-only (`src/video/restoration/runtime.py`, `get_codeformer_runtime_issues`, `get_realesrgan_runtime_issues`); install with `scripts/bootstrap_windows.ps1 -WithPostprocess`.
- **Face restore is temporally stabilised [V]** (`src/video/restoration/temporal.py`, on by default, `face_restore.temporal_smoothing`). CodeFormer still restores each frame, but the frames of one clip share a `TemporalFaceStabilizer`: the five detected landmarks of each face are tracked across frames and smoothed with an exponential moving average (weight 0.4 on the new frame) before the helper derives the crop and paste-back transform from them, and the restoration residual (restored minus input, in the aligned face crop) is averaged against the previous frame's (weight 0.5), ignored where the aligned crop changed a lot so real expression is never ghosted. A track starts over on a jump larger than one eye distance, a detector dropout longer than two frames or a scene cut (a 16x16 luma thumbnail difference above 32). A face the network failed on is left unrestored and forgets its history. It is deterministic arithmetic over landmarks and crops, tested with synthetic data; its effect on real footage has not been measured (the eval kit is the place to judge it), and the face-parsing paste mask is still computed per frame. The manifest records the smoothing counters (`postprocess.face_restore.worker_report.temporal`). `fidelity_weight` defaults to one value everywhere (`DEFAULT_FACE_RESTORE_FIDELITY` = 0.85, used by the dataclass, `from_dict`, `SVDController.build_default_config`, the tab and the worker); a stored value is never rewritten.
- **Upscale picks native 2x weights for a 2x request [V]** (`src/video/restoration/upscale_models.py`, `resolve_upscale_model`). Order: `upscale.model_path_x2` when it exists, else `RealESRGAN_x2plus.pth` beside `model_path`, else the general model (`RealESRGAN_x4plus`) resized to the request, which is the fallback and is recorded (`postprocess.upscale.model_selection`: weights, `source`, `fallback_reason`; the worker adds the network's actual `native_scale` and whether it `resized`). Only an exact 2x request prefers 2x weights; every other scale uses the general model. A configured 2x path that does not exist blocks admission (`RealESRGAN x2 weight`) rather than falling back quietly; with 2x weights alone a 2x request needs no 4x file. The RealESRGAN capability line in the tab says which one a 2x request would use.
- RIFE runs the external `rife-ncnn-vulkan` executable (`src/video/rife_runtime.py`, shared by SVD and finished Comfy clips). It is resolved in order: config `executable_path`, `STABLENEW_RIFE_EXE`, `PATH`, then `tools/rife` and one folder level below it (a release unpacks into a versioned folder; not shipped). The model is always named: the configured `model_dir`, else the newest complete `rife-v4.x` folder beside the executable (the executable's own default is an old model that rejects a custom frame target). Every command and the model are recorded under `postprocess.interpolation` (`commands`, `model`). Multipliers 2 and 4 only; the default is x2 for a source of 14 fps or more and x4 below (`default_rife_multiplier`), so the export lands at 24 fps or more; the effective export fps is derived by `get_effective_svd_export_fps`.
- **Smoothing is on by default only for new configs [V]:** `SVDController.build_default_config` (and `apply_recommended_svd_defaults`) enable interpolation when a RIFE executable resolves and leave it off otherwise; a frozen NJR keeps the values it was admitted with, and a saved tab state keeps the operator's choice. A missing runtime or model folder is refused by `validate_svd_postprocess_config` before generation, with a message that names Locate RIFE, `STABLENEW_RIFE_EXE` and `tools/rife`.
- **Loop and ping-pong export [V] (`src/video/loop_export.py`):** `output.loop_mode` (`none` | `ping_pong`) and `output.extend_to_seconds` (0 = off, at most 60) shape the exported sequence after post-processing, at the rate it plays. The ping-pong cycle is `frames + frames[-2:0:-1]` (no repeated end frames) and an extension repeats whole cycles, so the loop point stays seamless. The request is dry-run in `validate_svd_postprocess_config` (frame limit 3600) so an impossible one fails before generation. The run manifest and history record carry `export` (`mode`, `cycles`, `base_frame_count`, `output_frame_count`, `output_seconds`); `frame_count` is the exported count. Comfy clips are not looped yet.
- **GFPGAN is retired [V]** (owner decision D8, audit E3). The SVD tab offers only CodeFormer (`OFFERED_FACE_RESTORE_METHODS`) and a saved tab state that names GFPGAN turns face cleanup off with a status line instead of switching engines. The `"GFPGAN"` method value and `gfpgan_weight_path` stay valid in `SVDFaceRestoreConfig` only so a stored config or NJR still loads and displays; `validate_svd_postprocess_config` refuses an *enabled* one before any generation (`SVDController` at admission, `SVDRunner.run` for a queued or replayed job) with `GFPGAN is enabled but required runtime assets are missing: ... GFPGAN runtime (not part of the supported postprocess profile)`, and a disabled one is inert. The worker refuses the method too. Removal condition for this compatibility: delete the method value, `get_gfpgan_runtime_issues`, `GFPGAN_UNSUPPORTED_ISSUE` and the capability entry once no stored record can name it (an owner decision about old job history).
- **Post-process subprocesses are bounded and cancellable [V]:** `SVDPostprocessRunner._run_child` runs the worker and RIFE through the shared `run_bounded()` (`src/utils/managed_process.py`): 1800 s wall-clock timeout, capped stdout/stderr, the child runs inside its own job object (fail closed on Windows: if it cannot be contained it is not run and the stage fails with `could not start: containment unavailable`) so a kill reaches the whole tree, and the job's `CancelToken` stops the child (audit B8, fixed in P3-3). A timeout raises `SVDPostprocessError`; a cancel raises `CancellationError`. There is no per-stage progress inside a worker.

### 3.3 Encoding

Every MP4 written from frames goes through `VideoCreator.create_video_from_images` (`src/pipeline/video.py`) [V]: frames are staged, in the order given (never re-sorted by name), as `frame_%06d.png` in a private folder next to the output and read by the image2 demuxer at an integer `-framerate` (exact frame timing). `build_video_encode_args` applies `VideoEncodeSettings`: libx264/libx265 CRF (default 16, profiles `draft` 20, `balanced` 16, `archival` 12; a legacy `quality` value that names an x264 preset still selects the preset), even dimensions, a BT.709 RGB->YUV matrix with BT.709 primaries, transfer and matrix tags stamped on the frames (`setparams`, since FFmpeg lets frame properties override output-level tags) and `+faststart`. The encoder runs through `run_ffmpeg` -> `run_bounded()` (900 s bound, contained, capped output); a cancel raises `VideoEncodeCancelled` (surfaced as `CancellationError` by `src/video/video_export.py`) and removes the partial file. GIFs use one palette for the whole clip (`palettegen`/`paletteuse`) when FFmpeg is available, Pillow otherwise. Movie Clips assembly uses the same settings: its `-filter_complex` graph ends with `build_video_encode_filter()` and it takes `build_video_encode_args(include_filter=False)` (FFmpeg refuses `-vf` on a filtergraph output). A multi-segment sequence assembles through the same engine (section 7.1).

### 4.3 Building the job (`VideoWorkflowNjrBuilder`)

1. `validate_form_data` / `capability_errors`: required inputs derived from the spec, opt-in required for experimental specs, controls the spec does not declare are refused (not dropped).
2. `freeze_inputs`: concrete seed (`parse_seed_input`, never generated at run time), driving-video path and SHA-256 (or, when the form carries a `prepared_motion_source` record, the re-verified prepared clip plus the record; a `motion_source_preparation_blocked` reason is refused as-is), declared source preparation (`prepare_declared_workflow_source`: EXIF transpose, cover resize, centred crop to the catalog target, published as a StableNew-owned PNG with its hash) and source hash.
3. `build_job`: writes the `video_workflow` stage config (workflow id/version, prompt, `video_execution` block, `frame_count`/`fps` when the spec declares a policy, `operator_controls` via `resolve_operator_controls`, `pose_video_path` and `pose_video_sha256`, `source_preparation`), `extra_metadata["video_workflow"]` (including `governance_state`, `experimental_opt_in`, `source_identity` for batches) and calls `ReprocessJobBuilder`.

The same builder serves a normal submission, every arm of a one-variable experiment (`VideoWorkflowExperimentService`; arms must differ only in the chosen control; admission via `ExperimentAdmissionService` in `src/learning/experiment_execution.py`) and a multi-source batch of 1-25 images (`VideoWorkflowBatchService`: `assess`, `preview`, `admit`; one `submit_njrs` call; provenance descriptor `stablenew.batch.v1`, 0-based `source_index`). Do not create another path that builds a video NJR.

A finished experiment is reviewed, not re-run: `src/video/video_review_group.py` rebuilds the study from the persisted arms (any job id reopens it, after a restart too), `src/video/review_preview.py` decodes bounded, downscaled, read-only preview frames, and `src/learning/video_review_service.py` records the operator's per-clip quality assessment as Learning evidence (section 5.1). It queues, retries and scores nothing.

Fun Control's exact-prepared policy additionally freezes reference hashes, a graph digest, the model manifest and resource-policy identity. It requires a concrete seed and an accepted, ordered-frame-verified motion record at 24 FPS. Preview Frozen Plan uses the existing one-source batch worker and remains available while hardware is unqualified; Queue and canonical JobService admission refuse the 1.0.0 resource policy and enforce the 1.1.0 trial floor. Admission and execution share normalized neutral-intent workflow identity. Readiness explains explicit preparation without predicting automatic raw-clip trimming, padding or speed changes. Local size/hash verification and hash-verified upload snapshots apply to this declared policy; older workflows retain their existing contracts.

### 4.4 Execution (`ComfyWorkflowVideoBackend.execute`)

Order: registry governance check (an unknown/disabled/un-opted-in workflow never starts a runtime) -> frame-count legality -> `_verify_required_launch_flags` (the configured `comfy_command` must contain the spec's flags; an external runtime's flags cannot be proven, so it is refused) -> `RuntimeTransitionCoordinator.prepare_for(RUNTIME_COMFY)` -> `_ensure_runtime_ready` (managed launch or an already-healthy endpoint) -> `/object_info` -> `ComfyDependencyProbe.probe_workflow` (stock nodes, model files, custom nodes) -> `WorkflowResourceReadiness.evaluate` when the spec declares `resource_readiness` (fails closed if the driver figure cannot be read) -> `WorkflowCompiler.compile` -> `queue_prompt` -> `_wait_for_history_entry` (liveness reported every 5 s through `_prompt_is_live`) -> `_localize_comfy_outputs` (downloads `/view` outputs into the run dir; only `type: output` files count) -> `_write_manifest` (`<run>/manifests/<stem>.json`: compiled workflow, dependency probe, queue response, history entry, control record, actual runtime identity) -> optional secondary-motion re-encode.

**Frames out (PR-VID-WAN-324).** A spec whose `backend_defaults["output_policy"]` is `{"mode": "frames", "fps": N}` ends its graph in `SaveImage` (lossless PNG) instead of `CreateVideo`/`SaveVideo`. After localizing, `execute` puts the frames in numeric playback order, encodes them with the one StableNew encoder (`src/video/frames_out.py`, CRF 16, BT.709 tags, cancellable), makes that clip the primary output and leaves the PNGs in `frame_paths` (the first is the thumbnail). The manifest's `frames_out` block lists every frame's path and SHA-256 (the container metadata and the result carry a summary: counts, the exact last frame's path and SHA-256, and a digest of the list), plus the count the job froze at admission and a `reconciliation` of the two (`match`, `missing`, `extra` or `missing_and_extra`, with any gaps or repeats in Comfy's frame counters; `unverified` when no count was frozen). A listed frame that is missing on disk or does not decode fails the job before anything is encoded, and the encoder runs with `require_all_frames`, so it fails rather than skip a frame: every recorded hash is a frame of the clip. A count that does not reconcile is logged and recorded but does not fail the job (owner decision 2026-10-21). The acceptance wrapper `tools/acceptance/vid324_frames_out_acceptance.py` requires `match`, re-hashes every PNG and the last frame, decodes the MP4 with FFprobe to check its frame count and rate, and checks that the job's artifact, manifest and clip are one identity. Smoothing requested for such a clip reads the PNGs (`interpolate_frame_files`) instead of decoding the encoded clip. The Wan TI2V-5B frames-out spec is `1.3.0` (`_build_wan22_ti2v_5b_i2v_v1_3`): the 1.2.0 graph with node 11 `SaveImage` in place of `CreateVideo`/`SaveVideo`. It was **approved by the owner on 2026-10-21** after real acceptance runs (`tools/acceptance/vid324_frames_out_acceptance.py`: every frame's hash, the exact last frame, the encoded clip's decoded frame count and rate), so the picker offers it and 1.2.0 stays approved so stored jobs replay on their exact graph. A frozen count that differs from the frames saved is **recorded** (`reconciliation`), never a failure (owner decision 2026-10-21). No published version changed.

When the spec's `runtime_policy.release_owned_runtime_after_job` is true (Wan2.2 TI2V-5B from 1.1.0, every Wan-Animate-2 version and A14B), `execute` stops the Comfy that StableNew owns on every exit path (`BaseException`), through `ComfyProcessManager.stop()` only; a not-owned runtime is not asked to stop.

**Cancellation.** Workflow preparation and downloads check the runner's token at safe boundaries.
Runtime readiness and history polling wake when the token is signalled. In-flight HTTP requests retain
their transport bounds. When Comfy acknowledges a prompt ID, cancellation can request a stop for that
prompt alone. An unknown dispatch outcome remains ambiguous and the POST is never replayed.

**Warm reuse between consecutive jobs (VID-WARM-373).** A release-after-job spec may also declare `runtime_policy.keep_warm_between_jobs_seconds` (A14B 1.0.0: 120, owner request 2026-11-21; the graph is unchanged and the spec digest was re-pinned deliberately; Wan-Animate-2 driving video 1.3.0: 120, a new revision with the identical graph). After a *successful* job, `execute` then arms the one process-wide warm hold (`src/services/runtime_warm_hold.py`) for the owned process instead of stopping it, and records `runtime_release` as `{"policy": "keep_warm_between_jobs", "held": true, "pid", "idle_release_seconds"}`. Every later Comfy job claims the hold before it touches the runtime: the same workflow id and version on the very same owned pid reuses the process (`runtime_reuse.status == "warm"`, and readiness records it as warm for the RAM advisory and skips the GPU-memory probe for consecutive standalone jobs), while anything else held is released first, so that job starts exactly as it would have without the hold. Any `RuntimeTransitionCoordinator.prepare_for` (a WebUI, SVD, Diffusers or Comfy still-image job) also ends the hold first, through the release the backend registered. A failed or cancelled job releases as before and holds nothing; a watcher spawned through `ThreadRegistry` releases the hold when the idle grace passes. At application shutdown
the registry signals the watcher and prevents another hold. After queue execution and the watcher have stopped,
the application shutdown coordinator asks the existing Comfy process manager to release the runtime it owns.
A live runtime user defers release to the existing interpreter-exit cleanup. External runtimes stay under
their original owners. The hold's release stops only the pid it held and only while StableNew still owns it, so a relaunched or external runtime is never stopped by a stale hold. ### 4.5 Managed Comfy runtime

Identity lives in `config/managed_comfy_runtime.json` (ComfyUI v0.38.0 at a pinned commit, CPython 3.13 standard GIL, Torch 2.14.0+cu130, loopback only, required flags `--disable-pinned-memory` and `--disable-auto-launch`, no custom nodes) and `constraints/comfy-windows-py313-cu130-v0.38.0.txt`. Build: `scripts/bootstrap_managed_comfy_windows.ps1`; read-only verifier: `tools/runtime/verify_managed_comfy.py`; operator procedure: `docs/runbooks/managed_comfy_runtime.md`. It never shares an environment with the application (CPython 3.14).

`ComfyProcessManager` (`src/video/comfy_process_manager.py`) is the only lifecycle authority: it launches only when `probe_comfy_endpoint` says the endpoint is free, stops only the process it started, and never adopts an external one. The queue starts managed Comfy on demand after the selected job supplies its requirements. `build_default_comfy_process_config` uses the saved `comfy_command` with the documented environment override. The registered launcher retains its base command and records the effective argv separately for each owned child. The shared resolver in `managed_comfy_runtime.py` reads the managed installation contract and checks required switches against the selected ComfyUI source. Model integrity, hardware readiness and qualification retain their existing gates. Engine Settings > Video runtime (ComfyUI) can select a managed installation and show its configuration. `build_managed_launch_command` is pinned by a test to the verifier's `--print-command`.

Cancellation and failure semantics (audit B7, fixed in P3-3/P3-4) [V]: the managed child runs in its own kill-on-close job object (`src/utils/managed_process.py`), so a crashed StableNew cannot orphan it. `ComfyApiClient` goes through the typed `HttpTransport` (`src/api/http_transport.py`): `EndpointUnavailable` (never reached the server), `DispatchOutcomeUnknown` (a read timeout or a drop after sending: Comfy may already be running the prompt), `DefiniteRefusal` (HTTP error, bounded body) and `MalformedResponse`. `queue_prompt` is non-idempotent and is never retried; a `DispatchOutcomeUnknown` from it fails the job and must be treated as "possibly running". The history wait checks the request's `cancel_token` every poll (0.5 s): on cancel it asks Comfy to stop only this job's prompt (`POST /interrupt` with the prompt id if the prompt is running, `POST /queue {delete: [id]}` if it is still pending, nothing otherwise; failures are logged, never raised) and raises `CancellationError`. A job cancelled before dispatch queues nothing. A Comfy orphaned by a build that predates containment still looks like a healthy external one and StableNew refuses to launch or stop it. Do not add retries around `queue_prompt`.

## 5. Motion sources and guidance

- Still source: prepared and frozen before admission (4.3). Landscape/portrait/square handling is declared per spec (`source_preparation`), not decided by the backend. `preview_declared_workflow_source` computes the exact pixels and crop rectangle without writing, using the same transform as admission.
- Driving video (Animate-2 drive): path and SHA-256 frozen in the job; extensions `.mp4 .webm .mov .mkv`. `inspect_driving_video` (`src/video/driving_video_inspection.py`) is a bounded, read-only FFprobe/FFmpeg probe (wall-clock timeouts, byte-capped stdout, at most a few small preview frames, `file` protocol only, cancellable).
- **Prepare Motion Source** (optional, off by default): the operator picks a window start (and optional end) and whether to convert the clip to the workflow's declared rate; `prepare_motion_source` (`src/video/motion_source_preparation.py`, worker thread, bounded and cancellable) writes `<output>/prepared_driving_videos/<sha256>.mp4`, a lossless copy of exactly the `length` frames the workflow will consume, after decoding it again and requiring every frame to equal the planned source frame. An *enabled* request, meaning an intent in `observe` or `apply` mode or an enabled `secondary_motion` / `postprocess.secondary_motion` block, is refused before any dispatch at `JobService` admission, `PipelineRunner.run_njr`, replay compilation, SVD admission (`validate_svd_postprocess_config`) and the Comfy backend preflight; a disabled or absent one is inert. The engine, re-encode, worker action and policy service are deleted. What stays, so history is readable: `src/video/motion/` models, provenance and learning-metric readers, the config key and the manifest, container and Learning readers.
- **Smoothing a finished Comfy clip [V]** (`src/video/video_interpolation.py`): an optional, validated `interpolation` block in the workflow stage config (the Video Workflow form's "Smooth with RIFE") decodes the clip with FFmpeg, runs the same RIFE stage as SVD and re-encodes with `export_video_mp4`. The smoothed `<stem>_smooth.mp4` leads `output_paths`; Comfy's own file stays. The builder freezes the resolved executable and factor; the backend refuses an unsupported factor, a missing runtime or an unknown frame rate before the runtime starts; the record is under `interpolation` in the manifest.
- Camera presets, ControlNet/depth conditioning (`DepthMapResolver`, `_resolve_conditioning_inputs`, `_normalize_camera_intent` in the builder) are driven by the bindings a spec declares (`depth_map`, `camera_preset`, `controlnet_model`) and no catalog workflow declares them today [V]; they are kept as generic contract infrastructure and exercised by the synthetic conditioned fixture in `tests/helpers/video_contract_registry.py`. Whether to remove them (and the camera/depth controls in the Video Workflow tab) is a separate, product-visible decision.

### 5.1 Reviewing an experiment

Entry points: the Video Workflow tab's **Review Experiment...** (last queued arm, or empty to type a job id) and Job History's **Review Experiment** for a selected arm. `build_review_group` starts from one job id, accepts a sibling only when its own NJR is a `video_workflow` source carrying the same `LearningJobContext.experiment_id` (replay descendants and look-alikes are listed as excluded, never merged), refuses duplicate, out-of-range or diverging arms (it re-runs the PR-VID-194 `assert_one_variable` gate over the stored NJRs) and orders arms A to D by `variant_index`. Siblings come from `JobRepository.list_experiment_sibling_entries`, a read-only query over a bounded rowid window around the selected job (an experiment is admitted in one transaction, so its rows are adjacent); it adds no schema, index or cache. An arm is playable only when the repository says `completed` and its recorded `video_bundle` names an existing supported video file; every other state stays visible and nothing scans a folder.

The window compares any two playable arms with one clock (`ComparisonClock`): a step is `1 / max(fps)`, a lower-rate clip repeats frames, a shorter clip is held on its final frame, no speed is changed and each difference is disclosed. Frames are **review previews** (at most 120 frames, 256 px on the long side, 24 MiB per clip, decoded by the contained bounded FFmpeg path, nothing written); Open original hands the recorded file to the system viewer. Ratings (overall 1 to 5, a separate requested-action outcome, optional dimensions, notes, an optional manual preference) are append-only `video_workflow_quality_rating` Learning records keyed by job and artifact SHA-256 and isolated from image Learning (`docs/Subsystems/Learning/LEARNING.md` section 3.3). Detail and limits: `docs/Subsystems/Video/PR-VID-QUALITY-211_Experiment_Review.md`.

### 5.1.1 Controlled-motion evaluation (PR-VID-MOTION-410)

The eval kit (section 6) can evaluate whether an intended *source subject* reproduces a *driving reference*. A `stablenew.video-eval-suite.v2` case carries a `motion` object (driving file pinned by SHA-256, optional verified Motion Library binding, intended action, motion prompt, expected outcome, category, window, preparation mode, annotations); the driver belongs to the case, so one asset is evaluated across many source images without duplicating arms. v1 suites load unchanged and cannot carry a driver. Each job is still built by `VideoWorkflowNjrBuilder` and admitted in one `JobService.submit_njrs` call; `VideoEvalRunService` verifies the compiled NJR really froze the case's driver, prompt, library binding and preparation, re-hashes the source, prepared source, original driver and prepared derivative at admission, and refuses the whole run on any mismatch. A workflow that takes no driving video refuses a motion case; the driver is never dropped. `ratings.csv` adds subject attachment, motion fidelity (1 to 5), controlled observations and a driving-context digest beside the existing artifact digest, so a changed driver, derivative or source makes earlier motion ratings inapplicable (kept, not counted). The report adds integrity classes, a global image-motion diagnostic (labelled as such: not pose fidelity, not proof the subject moved), transfer summaries with explicit denominators, and the Motion Review window shows source, effective driver and results on one bounded clock. Limits: observed outcomes only, per-run evidence, no physical run made, the campaign templates are unexecuted. Detail: `docs/Subsystems/Video/PR-VID-MOTION-410_Motion_Fidelity_and_Transfer_Evaluation.md`; procedure: `docs/runbooks/video_eval_kit.md` section 9.

### 5.2 Motion Library (PR-VID-MOTION-LIB-353)

A local catalog of rendered motion-reference videos with search, bounded preview and a **Use as Driving Video** handoff (operator guide and limits: `docs/Subsystems/Video/MOTION_LIBRARY.md`). Package `src/video/motion_library/`: `ManifestStore` (`store.py`) owns `<root>/library.json` (versioned, atomic writes, corrupt or newer manifests refused and left untouched, interrupted managed copies recovered), `importer.py` adds a local file, a flat folder or a completed History clip, `verification.py` / `relink.py` decide whether a path is still the recorded SHA-256, and `handoff.py` decides what the tab may fill. It is application data, separate from the job repository and the model registry, and it imports no `JobService`, runner, backend or compiler (`tests/video/test_pr_vid_motion_lib_353_catalog.py` pins that).

The handoff fills only `pose_video_path`, after re-hashing the clip and checking that the **selected** workflow declares a driving video; it never picks another workflow, and it never previews or queues. Prepare Motion Source stays authoritative for what is consumed. The library identity (`{asset_id, sha256}`) travels in the form as `motion_library_asset` only while the field still holds the bound path; `VideoWorkflowNjrBuilder._frozen_library_asset` refuses the job unless that hash equals the frozen original clip, then records it under `extra_metadata["video_workflow"]["motion_library_asset"]`. This is provenance only: it adds no NJR field that any backend reads, and a stale or swapped clip fails closed. Importing, tagging, searching and previewing never queue a job, start a runtime, use the GPU or touch the network. FBX/BVH/AMC are not accepted; render them to video first (Blender steps in the operator guide). The library proves only that a clip is findable and verifiable, not that any motion transfers well.

**Harvested motion assets (PR-VID-MOTION-400).** Three things stay distinct: the *original source* (read-only), a *harvested motion asset* (a library clip holding exactly the chosen frames, workflow-independent, with a `HarvestRecord` for the original's SHA-256, frame window, cadence and lineage) and the *prepared driving source* (the 210 output for one workflow, whose contract stays authoritative). **Harvest Motion** opens from Recent outputs, Job History, Movie Clips, Storyboard and the Motion Library, hands over one exact file plus a claim, and never submits a job; it is an offline operation that reuses the 210 lossless, frame-verified, content-addressed engine and adds no runtime, GPU or NJR path. A harvested clip is applied through the same Use as Driving Video handoff, with optional provenance-only `derived_from` lineage; no engine, opt-in or qualification state changes. Design, limits and code map: `docs/Subsystems/Video/MOTION_LIBRARY.md` section 7; operator procedure: `docs/runbooks/motion_harvesting.md`; direction: `docs/Subsystems/Video/CONTROLLED_MOTION_ROADMAP.md`.

**Eval kit (PR-VID-EVAL-320) [V].** Candidates are compared with an eval run instead of a per-candidate qualification package (operator procedure: `docs/runbooks/video_eval_kit.md`). A suite (`src/video/video_eval_suite.py`, `stablenew.video-eval-suite.v1`) fixes cases (source image pinned by SHA-256, prompt), arms (an SVD configuration or a Video Workflow form, merged over the tab defaults) and one seed. Flags are guardrails, never a ranking; the owner's rating decides. **Identity and continuity acceptance (PR-VID-QUALITY-351) [V].** The same report is also the operator's identity review: it verifies each case's source image against the manifest `image_sha256` (a missing or changed file is shown as such and never replaced), shows it beside every arm, and records structured judgments in `ratings.csv` (rubric `src/video/video_eval_rubric.py`: source fidelity, subject stability, temporal continuity, anatomy/object integrity, scene stability, requested action, a separate critical-identity-break answer, controlled failure categories, first-failure time). No physical identity run has been made with this tooling.

Qualification harnesses are operator-only code in `tools/qualification/vid*` and `tools/acceptance/vid130_wan_acceptance.py`; they are not part of the production path or CI. ## 7. Movie Clips and assembly

Movie Clips assembles existing outputs (stills, frames, generated clips) into one movie. It is a queued CPU workload on the canonical path (owner decision D6) [V]:

| Step | Where | What it does |
|---|---|---|
| Intent | `src/gui/views/movie_clips_tab_frame_v2.py` | The list order is the movie order (Move Up/Down; nothing re-sorts it). Add and Load Folder take images and videos; Set for Selected gives stills their own duration. Settings: FPS, codec, quality, mode, resolution, transition, clip name, music and fade-out. |
| Admission | `src/controller/movie_clips_submission_service.py` (`AppController.on_build_movie_clip` only delegates) | On a tracked non-daemon worker: builds the intent, freezes it and crosses `JobService.submit_njrs` once; reports the job id or the refusal on the GUI thread. |
| Compiler | `src/video/movie_assembly_compiler.py` | `freeze_movie_assembly` reads every input once: the EXIF-oriented size of an image, a bounded FFprobe of each video (`inspect_driving_video`) and of the audio track, and the SHA-256 of each. "Match first clip" becomes concrete even dimensions (long edge at most 4096) and the quality becomes a concrete CRF and preset. The frame plan is checked before anything is queued. `build_movie_assembly_njr` compiles the one-stage VIDEO NJR. |
| NJR | `config["movie_assembly"]`, schema `stablenew.movie_assembly.v1` (`src/video/movie_assembly_models.py`) | Clips in order (path, SHA-256, kind, size, hold or probed duration), target width/height/fps, transition seconds, optional audio (path, SHA-256, fade-out), encoder codec/CRF/preset, clip name. `input_image_paths` repeats the clip paths; `config["pipeline"]["output_route"]` is `movie_clips`. |
| Handler | `MovieAssemblyHandler` (`src/pipeline/run_stage_handlers.py`) -> `run_movie_assembly` (`src/video/movie_assembly_engine.py`) | Re-hashes every frozen input and refuses a missing or changed one (fresh run, replay and retry alike), stages stills as oriented RGB PNGs, runs one FFmpeg command through `run_ffmpeg` (contained, bounded at 30 s per output second within 900 s-4 h, cancellable), publishes the file under its final name only after success and writes `manifests/<clip>_movie_assembly.json`. Records `video_artifacts["movie_assembly"]`, `video_primary_artifact`, `movie_assembly_artifact` and one variant, so History lists and opens it. |

Two modes. **Sequence:** every image is one frame at the FPS (images only; a list with a video switches the tab to slideshow). **Slideshow:** a still holds for its duration, a video plays for its probed duration; every input is fitted to the target (`scale` with the aspect kept, `pad` with black, `setsar=1`), resampled to the target rate (`fps`) and cut to an exact frame count (`tpad` clone plus `trim`), then neighbours are crossfaded with `xfade` (offsets computed in whole frames by `plan_timeline`: the movie has the sum of the clip frames minus one transition per boundary) or joined with `concat` when the transition is 0. A transition longer than half of the shortest item is refused at admission. The optional music track is padded with silence or cut to the movie's length (`apad,atrim`), faded out (`afade`), encoded as AAC and mapped with `-shortest`; clip audio is not kept. Encoding uses the shared settings (section 3.3).

Cancel reaches FFmpeg through the job's cancel token (the partial file is removed). `frozen_input_checks` lists every clip and the audio track with its digest, so a retry is refused up front when an input changed. Not built: interpolation of a Movie Clips assembly (a sequence's assembled movie can be smoothed, section 7.1), per-video trims, clip audio passthrough.

A multi-segment sequence assembles inside its own job through this same engine (section 7.1). `send_history_job_to_movie_clips` and `video_workspace_handoff.py` only route an existing output into the tab.

### 7.1 Multi-segment sequences (PR-VID-SEQ-330-CORE)

A sequence is **one NJR, one queue row and one `PipelineRunner.run_njr` call** that runs N sequential internal segments (1-12, at most 972
requested frames in total). It is not a second queue, runner, lifecycle or process authority: SQLite keeps every job fact, and the ledger below is
only a checkpoint artifact. Backends are native SVD XT (`svd_native`) and approved Comfy workflows; one job uses one backend.

- **Admission** (`src/video/sequence_admission.py`, `svd_sequence_admission.py`; `VideoSequenceControllerMixin.submit_sequence_job`,
  `SVDController.submit_sequence_job`): the intent is frozen as a typed `SequencePlan` (`src/video/sequence_plan.py`) under the stage config's
  `sequence_metadata`. The plan is versioned (`schema`, `policy_version`) and carries its own canonical `plan_digest`; a plan whose content no longer
  matches its digest cannot be loaded. Per segment it holds a concrete seed (a blank or `random` seed is drawn once, at admission), the exact native frame
  count, workflow id and exact version, prompt and negative prompt (the values the job really carries: a blank negative becomes the workflow's default,
  an unset segment value inherits the job's, an explicitly empty negative stays empty and an explicitly empty prompt is refused for a workflow that needs one, naming the shot;
  a sequence does not also require the form-level prompt when every segment resolves to its own, while a single video still does;
  the dispatched prompt is always the frozen one), anchor policy (`carry_last_frame` or `provided`, with the image's path and SHA-256),
  and `overlap_frames` (default **1** for a carried anchor, **0** for an authored one). The plan also freezes the backend, the SVD model, the job's own
  experimental opt-in, segment 0's source image and hash, continuity and plan-origin provenance, the assembly settings and the colour-match setting.
  Refused before an NJR exists, never clipped or defaulted: an illegal frame count (Wan 4n+1, the SVD model's maximum), an unknown field anywhere, a
  missing, unreadable or non-image (a video file) anchor, an authored anchor that is not exactly the sequence's frame size, an unapproved workflow
  (an `experimental` one only with this job's recorded opt-in), a workflow needing inputs a sequence cannot supply (end anchor, driving video, operator
  controls), mixed frame rates or source preparation, native SVD segments may smooth (the plan then plays at the multiplied rate), a loop or ping-pong export, a transition, too many segments or frames.
- **Smoothing the cut (VID-FRAME):** a sequence or Storyboard take can smooth its *assembled* movie with RIFE. The
  choice is frozen as `cut_interpolation` (never `interpolation`, so no segment smooths its own clip); segments,
  hand-offs and cut manifests stay at native frames. Long cuts are interpolated in 200-frame chunks with a one-frame
  overlap (`interpolate_cut_frames`). The `_smooth.mp4` is the movie (primary); the native-rate movie stays as
  `retained_source` and is recorded under `assembly.native`. The form suggests it on when RIFE is found, and
  Storyboard takes use it whenever RIFE is found. Deterministic tests only; no physical RIFE run.
- **Carry-forward** is the exact last frame as a lossless PNG with a recorded SHA-256, never an MP4 path (`src/video/sequence_frames.py`). Basis
  `native`: the last PNG a frames-out Comfy workflow saved (byte-identical, cross-checked against the backend's own per-frame hashes) or, for native SVD,
  the last generated frame saved before RIFE, loop export or upscaling (`SVDResult.native_final_frame`, written under the run's `sequence/native`
  folder). Basis `decoded`: only for a workflow that ends in an encoded clip (TI2V-5B 1.2.0); the frames are decoded back out of the clip by the bounded,
  cancellable FFmpeg path, the ledger says so, and the decode is refused unless it yields exactly the segment's admitted frame count. A frames-out or
  native-SVD segment whose generated count differs from the admitted count stops the sequence, and so does a native-SVD segment whose saved frame count is not
  what its postprocess record gives (the generated count, times the multiplier when RIFE ran; interpolation that does not say its multiplier is refused) (the standalone frames-out policy is unchanged: there it is
  still recorded, not fatal). A missing, corrupt, non-PNG or hash-mismatched anchor is never handed to a segment.
- **Per-segment overrides** go through one allow-listed seam (`ALLOWED_OVERRIDES` in `src/pipeline/video_sequence_executor.py`;
  `_execute_video_stage(stage_config_overrides=...)`): a copy of the frozen stage config gets the segment's seed, frame count, workflow identity and
  prompts (SVD: `inference.seed`, `inference.num_frames`, `output.save_frames`). The NJR is never mutated; each segment's request carries
  `<job_id>_segNN`, so its files and manifest never collide with another segment's.
- **Warm runtime**: every segment is dispatched with `hold_runtime=True` (`VideoExecutionRequest`, default false), so a StableNew-owned ComfyUI is neither
  released after a segment nor on its failure. The executor makes **one** release attempt in `finally`, on success, failure, cancellation and any
  `BaseException`, through `ComfyWorkflowVideoBackend.release_for_sequence` and the existing ownership interface (`_release_owned_runtime`): only a process
  StableNew launched and still owns is stopped, only when a segment's workflow declares `release_owned_runtime_after_job`, and an external runtime is never
  adopted or stopped. A failed release is recorded in the ledger and never replaces the error that ended the sequence. The single-clip path is unchanged. Because a held
  runtime keeps its model in host RAM, the resource-readiness observation records whether a later segment is served by the same
  StableNew-owned process (`ComfyWorkflowVideoBackend._sequence_warm_pid`). RAM is advisory for cold and warm loads alike; the GPU-memory floor always applies.
- **Ledger** (`src/video/sequence_ledger.py`): `<run>/sequence_state.json`, written atomically (`atomic_write_json`) after every completed segment and
  before the next dispatches; a write failure stops the sequence before another segment starts. It records the plan hash, `completed_prefix`,
  `next_segment` and the state (`running`, `completed`, `failed`, `cancelled`, `interrupted`), and per segment: seed, counts, workflow, overlap, the image it
  was conditioned on (path, hash, basis), the hashed clip, frames and backend manifest, the final frame with its basis, how the segment was processed and
  whether it was `generated` or `reused`. A failed or cancelled run leaves the valid completed prefix and a pointer in the run metadata
  (`sequence_artifact.ledger_path`, `ledger_sha256`, `ledger_state`, `completed_segments`, `next_segment`). Only the failing operation's own uncommitted
  staging is removed; completed segments' files are kept.
- **Resume** (`src/video/sequence_resume.py`; `VideoSequenceControllerMixin.resume_sequence(parent_job_id, from_segment)`): a NEW NJR (new job id, replay
  parent lineage) with a frozen `sequence_resume` block (parent job, ledger path and SHA-256, plan digest, `from_segment`), admitted through
  `JobService.submit_njrs`. The checkpoint, the plan digest, the job identity, that every recorded path stays inside the checkpoint's own run folder, each
  prefix segment, and every reused file's hash (and PNG validity) are verified at admission and again before the runner dispatches anything; the prefix is
  *copied* into the new run directory (each copy re-hashed), so the child does not depend on the parent folder, and only the unfinished suffix runs. A
  tampered, missing, conflicting or unsafe file refuses the resume; it never falls back to a full rerun, never restarts the original job and is never
  automatic after a device loss. A segment that was in flight is simply the first segment of the suffix; no generation request is replayed. A job that recorded
  no result (a cancelled one) is resumed from the checkpoint found in its own run folder by job id (`src/video/sequence_locator.py`: the route folders
  of the output root, a folder named after the job, and a ledger that names that very job), or from a `sequence_state.json` the operator names (`ledger_path=`). `from_segment` may equal the segment count when only the
  assembly was left.
- **Full replay** (`replay_sequence`, and any History replay) is different: it recomputes every segment from the frozen plan and never inherits a resume. When
  the original ledger is available it is pinned, and the replay's ledger records per segment whether the recomputed final frame equals the original's
  (`replay.diverged_segments`); a GPU re-run is not guaranteed to be byte-identical, so divergence is recorded and never a failure.
- **Assembly** is inside the same job: the segments' frames in segment order, each later segment's `overlap_frames` dropped, are frozen as an ASM-332
  *frame sequence* (`MODE_SEQUENCE`, hard cuts at the plan's frame rate) and encoded by `run_movie_assembly` (`src/video/sequence_assembly.py`), the same
  engine and software-encoder contract as Movie Clips. Frames of mixed sizes are refused; the engine re-hashes every frame and honours the job's cancel
  token; the assembled timeline must equal the frames handed to it. No `movie_assembly` job is queued. A requested assembly that fails fails the sequence
  (the segments stay in the ledger); the assembled movie leads the job's outputs and carries the engine's manifest and hash. The bundle the job records as its primary video (what Recent outputs and
  Job History hand to Movie Clips) is that assembled movie alone; every segment clip stays listed in `sequence_artifact.all_output_paths`.
- **Colour matching** is opt-in and **off by default** (`SequencePlan.color_match`): one integer lookup table per channel per later segment, built from the
  segment's pooled histogram and segment 0's first frame, applied to derived assembly copies only; the carried anchors, the ledger's original frames and
  segment 0 are never altered, and the ledger records the algorithm, the reference hash and which segments were transformed. It does not address
  subject-identity drift.
- **Retired**: the pre-SEQ-330 sequence layer (`sequence_planner`, `sequence_models`, `sequence_manifest`, `ComfyWorkflowVideoBackend.execute_segment`,
  `AssemblyService` and the `-c copy` `stitch_video_segments`) had no remaining caller and was deleted. A stored `sequence_artifact`, assembled-video record or
  `AssembledSequenceInput` (and the `AssemblyRequest` type that names the retired service) still reads and loads; they stay until no stored record can name
  them. A job carrying a block in the old `total_segments` shape is refused with a readable reason instead of running.
- **Operating a sequence (PR-VID-SEQ-331A)**: the Video Workflow tab's Advanced area has a *Multi-shot sequence* section (`src/gui/views/video_workflow_sequence_panel_v2.py`,
  state in `src/gui/view_contracts/video_sequence_contract.py`, shot-to-intent in `src/video/sequence_shots.py`). An ordered list of 2-12 shots (prompt, a legal
  length of the selected workflow, an optional authored keyframe) becomes one `sequence_intent` for `submit_sequence_job`: shot 1 starts from the form's source image,
  a later shot with a keyframe uses the `provided` anchor (hard cut, no overlap frame dropped) and one without carries the exact last frame. Every refusal is
  admission's and appears inline; nothing is queued by a refused plan. *Check progress* reads the checkpoint's `completed_prefix` (evidence only). Job History
  (`HistoryActionState.sequence_resume` / `sequence_replay`, `src/video/sequence_history.py`, `src/gui/view_contracts/history_sequence_contract.py`) shows
  "n of N segments done" for a sequence job and offers *Resume Sequence* (failed or cancelled) and *Replay Sequence* (any finished job); both queue a NEW job through
  `resume_sequence` / `replay_sequence`, and a job whose checkpoint cannot be found asks for its `sequence_state.json`.
- **Persistent Storyboards**: the same Multi-shot sequence section saves versioned editable intent under `%LOCALAPPDATA%/StableNew/storyboards/`,
  separate from executable `SequencePlan` and repository jobs (`src/video/storyboard.py`, `storyboard_store.py`). Save/Save As/Open/Rename,
  JSON import/export and shot duplication/reorder never submit work. Atomic writes and exclusive per-draft revision checks refuse stale saves;
  malformed/future-schema files are preserved. Source and authored-anchor SHA-256 identities survive reopen; changed bytes require explicit acceptance.
  Readiness is an authoring projection with seed intent, legal native frames, approximate duration, workflow/version and source/anchor problems.
  Queue alone uses `build_sequence_intent` and the existing `submit_sequence_job` admission, verifying linked identities against the frozen inputs;
  unsupported controls (including Fun Control driving inputs) refuse. Background file operations use `EditWorkRunner` and drop disposed-view callbacks.
  History's *Create Storyboard from Sequence* rereads the canonical NJR through `src/video/storyboard_history.py`, verifies the typed plan digest and creates
  a new draft with provenance only. Homogeneous Comfy sequences with standard assembly/overlap are supported; native SVD model/settings, mixed workflows,
  per-shot negatives and custom assembly/color/overlap cannot be represented in this editor and are refused precisely. Existing SVD Resume/Replay is unchanged.
  [Operator guide and proposed suffix-regeneration boundary](STORYBOARDS.md).
- **Storyboard takes (PR-VID-STORY-380, execution package)**: the execution half of the storyboard tree of takes
  (spec `docs/superpowers/specs/2026-11-21-storyboard-tree-of-takes-design.md`). There is no Storyboard tab yet; that
  is a later package. Nothing here adds a queue, runner, history authority or direct GUI-to-backend path. One Continue
  is one `JobService.submit_njrs` call with 1-6 takes, each a normal sequence job; no watcher and no follow-up submission when a job finishes.
  - *Policy v2*: `SEQUENCE_POLICY_VERSION_V2 = "stablenew.video_sequence_policy.v2"` (`src/video/sequence_plan.py`). v1 is unchanged
    and a v1 plan's content digest is byte-identical to before (the `storyboard` key never appears in v1 content). A v2 plan may
    carry a `StoryboardPlanLink` (storyboard id, take id, parent, handoff index) and a lead-in (the exact handoff PNG and its
    SHA-256, plus the parent cut's frames to prefix). v2 always assembles and never colour-matches. Segment 0 of a take with a
    lead-in must start from the handoff frame (same hash, same normalised path). Native SVD takes are refused.
  - *Cut manifest* (`src/video/storyboard_cut.py`, `stablenew.storyboard_cut.v1`): the hashed list of frames that make up a
    cut, with ranges naming where each came from (root, lead-in, a segment) and how many were trimmed. `verify_lead_in` re-hashes
    every lead-in frame, so a moved or changed frame refuses before any GPU work. A take's own manifest is written in its run folder
    and referenced from the job's `sequence_artifact` (`src/video/storyboard_cuts.py` resolves a job's parent cut).
  - *Pass-through source*: a take with a lead-in starts from the exact handoff PNG. No source preparation runs and no substitute file
    is made (`src/video/workflow_source_preparation.py`, `exact_source`); admission refuses a handoff PNG that is not exactly the
    target size. A take never smooths its segments (its stitched cut is smoothed, below); a smoothed root uses its generated frames at the workflow's fps.
  - *Executor*: the sequence executor assembles the lead-in prefix (referenced, never copied into the take's segments) plus the
    take's segments, and the lead-in does not count against the 12-segment and 972-frame caps
    (`src/pipeline/video_sequence_executor.py`).
  - *Root preparation* (`src/video/storyboard_root.py`): a finished clip or an image becomes the storyboard root. Frames are decoded to
    `<output root>/storyboards/<storyboard_id>/root/` with a root cut manifest; an existing `root/` is refused, and a smoothed clip
    uses its generated frames at the workflow's fps with the fixed note about the smoothing. An MP4 chosen by file
    (`src/video/storyboard_import.py`, PR-VID-STORY-IMPORT) is matched to its job only by repository output-path evidence and
    then uses the same job route; any other MP4 is probed with `inspect_driving_video`, decoded once (`decode_clip_to_frames`,
    basis `decoded`) and published through `publish_root` as an `origin: external` root with an `import_record.json`.
  - *Storyboard file* (`src/video/storyboard_tree.py`, `storyboard_tree_store.py`, `stablenew.storyboard-tree.v1`):
    `%LOCALAPPDATA%/StableNew/storyboard_trees/<storyboard_id>.json`, written through `src/utils/atomic_io.py` with a revision
    compare-and-swap, an exclusive `.lock` and a 2 MB cap. It holds the root, the takes (parent, label, attempts, marks, job ids)
    and dispositions. Malformed or future-schema files are never rewritten. Drop only hides; no file is moved or deleted.
  - *Submission service* (`src/controller/storyboard_submission_service.py`): builds the rows into NJRs and submits them in one call;
    a failed submit keeps takes whose job id reached the repository and removes the rest (and their descendants). Opening a storyboard
    reconciles take states from job records (`src/video/storyboard_reconcile.py`), skipping unreadable records.
  - *Evidence*: unit and integration tests with fakes only. No physical GPU run is claimed for storyboard takes; native SVD takes are not supported.
- **Not here**: selective middle-shot rerender or suffix reuse, first-last-frame anchors (FLF-322), crossfades between segments, new Wan models. `PR-VID-SEQ-330_Acceptance.md` is the physical procedure (runs A-C passed on the RTX 4070 Ti on 2026-10-22; native SVD was not run),
  `tools/acceptance/seq330_sequence_acceptance.py` drives it and `tools/acceptance/seq330_sequence_verification.py` re-verifies a finished run's ledger and
  artifacts.
- **SVI reference pad and sequence evals (VID-A14B-SVI-375)**: the experimental `wan22_i2v_a14b_svi` workflow (section 4.2) is sequence-capable with
  the job's opt-in; its required `ref_pad_image` comes from the frozen `source_preparation` block (segment 0's prepared source), so it needs no new
  per-segment override. The video eval kit can queue a case of 2-12 segments as one sequence job per arm through `build_sequence_job` (segment *i*
  seeded with the suite seed + *i*), rate the assembled movie as one clip and verify the pair against every segment's prompt and seed
  (`docs/runbooks/video_eval_kit.md` section 2.1).

## 10. Invariants that must not be broken

1. Canonical path only. No second queue, runner, history or compiler authority; one NJR builder for Video Workflow (`VideoWorkflowNjrBuilder`). The GUI and controllers never call a backend, Comfy or `SVDRunner`.
2. The NJR is immutable. Seed, frame count, source, prepared source, driving video hash, controls and workflow version are frozen at admission; the backend must not derive any of them at run time.
3. Refuse before dispatch. Unknown backend, task, control, workflow, illegal frame count, missing dependency, unmet resource floor, missing launch flag: raise before the first Comfy `POST /prompt`. No silent fallback, no dropped control. Policy status is not a refusal (N1, `AGENTS.md` section 2); this invariant covers real blocks only.
4. Selecting Queue on a summary that shows an experimental workflow's warning records explicit per-job authorization (`video_execution.experimental_opt_in` and `provenance.metadata.accepted_warnings`, N1). This holds for a picked, restored, handed-off, Storyboard Continue or phone submission alike, because the warning is shown at the moment of Queue (the Video Workflow header and the Storyboard Continue summary show it as text, with Queue enabled). An eval suite arm keeps its authored per-arm opt-in, and the run confirmation names its experimental arms. Make Video never preselects an experimental workflow. Approved workflows need no opt-in. Replay reads authorization from the recorded job. Disabled and retired workflows stay ineligible.
5. Published workflow versions are immutable; a change is a new version and the old one stays registered.
6. StableNew controls lifecycle only for a Comfy process `ComfyProcessManager` launched. External Comfy is never adopted, stopped or restarted. Never replay an ambiguous dispatched prompt.
7. Native SVD and Comfy do not share residency: use `RuntimeTransitionCoordinator` before loading either.
8. Advisories and guidance (`motion_source_readiness`, `workflow_motion_guidance`) are display-only and must stay unable to change a job. `driving_video_inspection` is read-only; the only way it informs a job is through an explicit, operator-invoked preparation whose output is re-verified at admission (invariant 2 still holds: nothing is derived at run time).
9. Persisted state goes through `src/utils/atomic_io.py`; outputs are written under the run directory and partial outputs removed on failure.
10. The device-loss quarantine remains in effect on recurrence (see [DIAG-GPU-160](../Runtime/DIAG-GPU-160_PCIe_Gen4_Resolution.md)). No real SVD, Wan, Comfy start or qualification run without explicit owner authorization. Tests must not start Comfy, load a model or touch a GPU.
11. Protected actions (push to `main`, merge, publish, secrets, material architecture changes) need explicit owner approval (`AGENTS.md` section 5).
12. Experiment review is a post-execution consumer: it imports no runner, queue, backend or compiler, calls no submission, lifecycle or delete method, writes only Learning evidence through `LearningRecordWriter`, and identifies a rated clip by job and content hash, never by path alone (`tests/safety/test_video_review_211_architecture.py`).
13. The Motion Library is a catalog, not an execution authority: it never queues, never builds an NJR, and never moves, renames or deletes an original video. A library identity reaches a job only as provenance verified against the frozen driving clip (5.2).

## 12. Known debt and traps

- `src/video/comfy_workflow_backend.py` is 1,374 lines and mixes governance, readiness, upload, history polling, output localization and manifest writing in one class. Adding a Comfy-hosted model needs about 3 files; a native backend about 15 [A, audit E3].
- Workflow graphs are inline Python dicts, requalification mints versions, and the qualification record is embedded in the spec (`provenance`, `governance_notes`). Roadmap P4-6 [A].
- SVD uses the legacy resolver bridge (section 2); `SourceKind.VIDEO_WORKFLOW` is used for SVD NJRs [V]. Filtering history by "video workflow" therefore includes SVD jobs.
- No cancellation for Comfy waits or SVD post-process subprocesses; no timeouts on the latter (3.2, 4.5). Cancel only takes effect between SVD phases and denoising steps.
- `SVDRunner.run` returns a successful result even when optional post-process warnings were recorded; check `postprocess["warnings"]` (CodeFormer pastes an unrestored face back and only warns).
- The executor swallows non-SVD exceptions in `run_svd_native_stage` and returns `None`, which the runner reports as no output. `SVDError` subclasses propagate; raise refusals as those (`src/video/svd_errors.py`).
- `PipelineRunner._execute_video_stage` still names `svd_native` in places (filenames, postprocess merge, legacy metadata keys). It is part of the executor-sized `run_njr` debt (roadmap P4-1) [A].
- Disk space is not checked before SVD frame dumps or Comfy downloads (audit E6) [A]. A user-set `comfy_command` is not checked for `--listen 0.0.0.0` (audit E5) [A].
- Motion Library: no remove-from-catalog, no bulk re-verification, rendered video only; a catalogued clip says nothing about generation quality (5.2).
- `cv2` is used by restoration/refinement code but declared only in the SVD/postprocess extra [A].

## 13. Adding or changing video behavior today

- **A new Comfy workflow (experimental):** add a `WorkflowSpec` builder in `src/video/workflow_catalog.py` (or a sibling module like `workflow_catalog_wan_animate2.py`) and include it in `build_builtin_workflow_specs`. Pin model files by name and SHA-256, list stock nodes as dependencies, set `governance_state="experimental"`, declare `resource_readiness`, `frame_count_policy`, `runtime_policy` and operator controls in `backend_defaults` rather than in code. Do not add workflow-name branches to the builder, compiler or backend; add a neutral control if one is missing. Tests: registry, compiler, version-pinning and a `_FakeComfy` backend run. Qualification is owner-gated.
- **A new revision of an existing workflow:** a new version row; never edit the old one; update the version-pinning test.
- **A new neutral control or task:** extend `KNOWN_VIDEO_CONTROLS` / `KNOWN_VIDEO_TASKS` together with a backend that declares it and a workflow capability tag in `_WORKFLOW_TAG_CONTROLS`; update `requested_controls` and `capability_errors` in `src/video/video_workflow_intent.py`.
- **A new native backend:** implement `VideoBackendInterface`, register it in `build_default_video_backend_registry`, add a `RUNTIME_*` residency entry in `src/services/runtime_transition_service.py`, a branch in `src/queue/backend_dependency.py`, and have the producer write a `video_execution` block. Needs an owner architecture decision (`AGENTS.md` section 2 names the production video backends).
- **Promoting a workflow to `approved`:** owner decision (the P3-3 and P3-4 preconditions are merged). Promote only the version the picker offers: give that version's builder a non-experimental `governance_state`, display name, description and notes, leave older versions untouched (their digests are pinned), and update the version test deliberately. Then update sections 1.1, 4.2 and 9 and `STATUS.md`. The tab asks for no opt-in and `build_optional_dependency_snapshot` lists the workflow without starting anything.
- **A new SVD post-process stage:** extend `SVDPostprocessConfig`, `validate_svd_postprocess_config`, `SVDPostprocessRunner.process_frames` and `get_svd_postprocess_capabilities`; run it as a bounded subprocess with a timeout and the cancel token (`run_bounded`), not as another unbounded `subprocess.run`; decide where it sits in the stage order (3.2) and record it in `postprocess.stages`.
- Update this file, `STATUS.md` (supported capabilities) and, for qualification evidence, a record under `docs/Subsystems/Video/`.
