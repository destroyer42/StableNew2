# Migration and backward-compatibility risks

**No migration, schema change, user-data read, cleanup or restore ran in D.** These are prerequisites for later approved work. Existing application stores remain authoritative. A new metadata schema, durable state or compatibility policy is a material decision, even when it does not execute jobs.

## Minimum future migration contract — candidate, not authorization

Before any approved migration, the owning implementation package must enumerate source/target schemas and readers; preserve user-owned inputs; choose an offline or explicitly quiesced write window; create and verify recoverable backups under the existing owning boundary; dry-run into isolated temporary targets; report identity/duplicate/conflict/missing dependencies; verify every authoritative reference; and define rollback without overwriting newer approved work. An unsupported schema, unresolved conflict or unknown job admission must stop continuation.

For metadata recovery, default to a new draft/import namespace with explicit review. For immutable job/profile/evidence history, preserve the original record and use new identities/versions where appropriate. For executable NJR upgrades, only the approved repository/compiler boundary may convert, with deterministic round-trip and compatibility tests. There is no new universal migrator, restore service or rollback authority in this research.

No disk-space estimate, archive safety claim, user-data deletion list or runtime/deployment readiness follows from this document. Those depend on live identities and separately authorized operations.
