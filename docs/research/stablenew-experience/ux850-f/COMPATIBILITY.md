# Existing-user compatibility, migration and rollback requirements

P1–P6 propose no schema migration, disk relocation, deletion, backend/runtime upgrade or change of persisted consent. Preserve [D M01–M20](../ux850-d/MIGRATION_COMPATIBILITY.md) as conditional design constraints; they are not approval of a migration or a promise that current stores have universal durability.

## If a later selected outcome needs migration

Freeze source/target schemas, supported readers and exact identities; inventory dependencies without publishing private user files. Owner chooses backup/retention/conflict/destructive semantics and authorized offline or explicitly quiesced write window. Dry-run into isolated temporary targets, verify backup recovery, validate identities/missing links/duplicates, refuse unsupported/corrupt/conflicting inputs, and test restart/idempotency/partial-write behavior. Preserve originals and immutable history; never overwrite newer user work during rollback. New metadata defaults to explicit review/new namespace where approved, not guessed historical backfill.

Separate code rollback, schema compatibility rollback and user-data recovery. Reverting code does not make a destructive conversion reversible. A failed migration retains original data and an explicit report; no silent partial adoption or live legacy runner fallback. Actual operation needs current explicit target authorization and security review. F neither selects such an operation nor assesses disk capacity/archive safety.

P1 specifically changes only whether deliberate Load can replace dirty in-memory work: declining retains it, accepting uses current loader. Same-pack reload is not a new saved-document version. This is prevention within a current owner, not recovery across process exit. Full shutdown/autosave policy remains R1/G1.
