## GUI-FOUNDATION-851 — candidate first implementation package

**Problem/outcome:** users must reach the controls and recovery information needed to complete T1/T2/T8/T9 at supported short-window sizes without lost clicks or hidden primary actions. Historical layout/scroll evidence motivates measurement; it does not establish a current defect at today's SHA.

**Execution Profile:** Standard only if a current reproduction is presentation-only under existing owners; Architectural if it needs new lifecycle state, composition authority, toolkit, saved-ID migration, or minimum-size policy. Stop at that boundary and return a concrete decision; do not silently expand.

**Model recommendation:** Claude Code Sonnet 5.5 High / Codex GPT-6.1 Sol High, Local/Desktop for Windows fixtures and local source. Expected total-success cost favors one current-baseline pass and one coherent presentation repair over a new shell/framework plus migration. Escalate only a demonstrated ownership ambiguity to Opus 5.5 High / GPT-6 Astra High in its separate contract.

**Entry/reproduction gate:** inspect current source and choose the smallest relevant safe test fixture. Run an isolated fake-backend baseline only after its desktop-control preconditions are satisfied, including explicit owner availability confirmation where the existing harness contract requires it. No owner's running app, backend startup, GPU, model inference or global scale change. Start with source/pure contract tests if desktop testing is unavailable; do not claim usability acceptance from them. If nothing material reproduces, record no-code PASS and stop.

**Likely scope, selected by evidence:** existing layout/view contracts, ScrollableFrame focus/wheel behavior, compact status/details presentation and primary-action placement. Preserve nine production destinations/stable IDs, default startup route, expert capabilities, content visibility and repository lifecycle. Do not add general Library storage, lock scopes, a new Preparing durable status or AI dependencies in this package.

**Controller Surface Assessment:** presentation adapters and existing Tk dispatcher only. No added responsibilities in ratcheted controllers, no changed ceilings, no second pump. If a cohesive service extraction is necessary for correctness, name its single owner and retain existing call boundary. Run current controller-surface and Tk-boundary checks near closeout if those surfaces change.

**Acceptance:**

- A named current defect is reproduced with exact fixture/SHA and corrected with one relevant regression test; or no-code PASS records that no in-scope defect exists.
- The named actions remain reachable at 1280×680 and the 1280×760 comparison, with honest client-size/scale evidence. Keyboard and mouse press/release behavior both pass; stationary-pointer focus case included when relevant.
- Existing task IDs/navigation persistence remain equivalent. No mutation of PromptPacks/settings merely from navigation or inspection.
- Existing compile/frozen-preview/admission contract and Run Now enqueue behavior remain intact; no duplicate jobs or guessed recovery.
- Status text does not disagree with canonical queue/repository state. A presentation label is not persisted as a new lifecycle.
- Comparative measurements demonstrate the claimed improvement or explicitly report inconclusive/no improvement. No real-model output claim.

**Token-Efficient Validation Plan:** acquire current state once; reuse unchanged evidence; reproduce one failure class before edit; run its focused tests plus relevant navigation/layout/submission contracts; perform one aggregate review and bounded repair; run policy-selected late PR gate once; inspect exact-SHA required/full-suite/Windows CI as applicable. Avoid full GPU/physical campaigns or repeated broad suites. New failure classes beyond the package's stop rule are reported, not accumulated as scope.

**Exclusions:** toolkit migration, new visual theme, higher minimum viewport, model/runtime configuration, campaigns, schema migration, storage cleanup, physical qualification, publication/merge. Architecture effect should be presentation-only; any different discovery escalates before implementation.

**Acceptance and evidence boundary:** implementation = scoped presentation change or justified no-code disposition; demonstration = named deterministic tests plus authorized isolated Windows observations; qualification = N/A; held = real model/GPU quality and unmeasured DPI conditions. If desktop evidence cannot be obtained, label acceptance partial and leave the required observation open rather than converting source tests into usability proof.

## Decisions that still matter

The register already resolves broad workflow preferences and lock scopes. Do not ask those again. The next owner discussion should review this concrete design and address only material choices:

1. **First release acceptance:** select the foundation outcome and first operator journey, or move a documented blocked Learning/Motion outcome ahead. Recommendation: foundation with Create as the proving journey; no-code exit if no defect reproduces.
2. **Confirmation:** reconcile ready-work one-click UX-DEC-004 with prior mandatory visible frozen preview/Confirm & Queue. Recommendation: preserve explicit frozen review for material changes and AI plans; define any ready/repeat fast path precisely before implementation.
3. **Production navigation/data scope:** approve a Library destination and saved-ID transition only when the connected package is concrete. Recommendation: read projection first, no destructive cleanup or copied History authority.
4. **AI boundary:** adjudicate the already-written D-1–D-5 amendment before model-assisted executable planning. Recommendation: deterministic/manual core first; do not repeat the broad AI preference discovery.

Qt/Tk comparison, campaign authority, destructive archival, evaluator release and suffix-regeneration decisions are later conditional gates. They need evidence and their own contracts, not an immediate questionnaire. UI color/spacing/file selection/test selection are routine technical work and do not need additional owner approval.

## Evidence, migration and release plan

Start additively and preserve user stores. A visual reorganization should not migrate jobs/media/ratings. New draft/lock/collection schema work must define unknown-version refusal, atomic writes, conflict behavior, backup/restore and exact compatibility scope before writes. Existing saved numeric tab order is preserved until a specifically approved transition. Opening the redesign must not automatically import, archive, prune or delete historical data.

Use isolated fake workflows for functional acceptance, exact current required CI for integration and separately authorized Windows observations for usability. Qualification remains in its existing authority; this plan creates no registry. Feature-branch publication, merge, release and deployment remain distinct owner-authorized actions. At package closeout include exact SHA, accepted evidence/limits and measured host/session usage; then hand off to a fresh session for the next functional package.

Framework improvement: future UX assessments should collect the current source lock, owner register and six-factor evidence table in one intake, then challenge stale proposed work against integrated code before opening new discovery questions. This avoids confusing a named capability, an implemented path and a demonstrated operator outcome.
